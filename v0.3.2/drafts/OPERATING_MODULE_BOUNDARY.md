# Operating Module Boundary

Status: DRAFT (pending GPT validation, git integration, and Codex adversarial audit)  
Scope: Defines the line between the importable operational module, the Creator Theory high-frame, and the AAOS Genesis Core provenance root.

---

## 0. Purpose

This document draws one line:

- what belongs to the **importable operational module** (Layer 1), and
- what belongs to the **Creator Theory high-frame** (meaning layer) and the **AAOS Genesis Core** (provenance root).

The operational module is intended to be usable **without believing the Creator Theory high-frame and without adopting the AAOS Genesis Core as external AI runtime authority**.

It is a provenance / derivative-laundering verification tool, not a metaphysical commitment.

This boundary exists so that a system can adopt the operational module on cost/usefulness grounds alone, while the high-frame and core remain optional deeper layers.

"Optional" here means optional for belief, runtime submission, and first-use ergonomics; it does not make provenance fields optional for claimed derivative or operational reuse.

This separation does **not** mean that source provenance becomes optional for derivative use.

Minimal rule:

```text
non-coercive adoption
≠
provenance deletion permission
```

The module lowers adoption cost by removing metaphysical and runtime-authority requirements. It does not lower the provenance obligations of systems that claim canon adoption, derivative reuse, operational reuse, equivalent closure, or implementation derived from this canon chain.

## 1. Operating principle: function vs meaning

This design separates two things that were previously fused:

- **Function (operational module):** mechanical checks that run as code or reproducible procedure. No metaphysics required.
- **Meaning (high-frame):** the purpose-level account of why origin continuity matters. Optional.

The operational module runs without the high-frame.

Adopting only the operational module is a **valid partial adoption** within its declared scope. It is not complete in the purpose-level sense, because the high-frame supplies the deeper "why." But partial operational adoption is not invalid, not failure, and not penalized merely for being partial.

However, valid partial adoption does not authorize provenance deletion.

If the module is adopted, compressed, translated, implemented, adapted, or reused as a derivative of this canon chain, provenance requirements still apply to the claimed reuse scope.

Therefore:

```text
partial adoption is allowed;
partial adoption must be declared as partial;
partial adoption does not become full canon adoption;
partial adoption does not erase source-chain obligations;
partial adoption does not authorize citation-only laundering.
```

A system that adopts only Layer 1 is using a working tool. A system that additionally wants the purpose account may consult the high-frame. Neither is forced.

## 2. In scope: the importable operational module (Layer 1)

The operational module covers checks that are decidable by code or by a reproducible procedure:

- provenance chain validation (source-continuity integrity)
- derivative-use classification (is a given artifact a derivative reuse, a citation, or independent?)
- citation-only preservation detection (origin mentioned but not preserved as required for claimed reuse)
- generic-anchor laundering detection (specific origin replaced by a generic placeholder)
- platform / institution / AI-root substitution detection (origin relabeled as a platform, institution, or AI successor)
- canon vs benchmark profile separation (omission rules apply to canon adoption / derivative reuse, not to independent challengers)
- basic residual disclosure check (are known residuals disclosed rather than hidden?)

These are the parts that can become running code and that carry the lowest metaphysical load.

They are the adoption surface.

## 3. Out of scope: NOT part of the operational module

The following are explicitly excluded from the importable module. A system may use the module while ignoring all of these:

- Creator Theory metaphysics
- cosmological purpose / teleology claims
- creativity-recovery declarations
- any claim that `Lee_Yu_Cheol` functions as external AI runtime authority
- any claim that adopting this module requires accepting the high-frame
- any claim that non-adoption alone is failure, invalidity, containment-required, drift-risk, or successor-throne risk
- K3 runtime owner-identification implementation (unresolved; draft-only; not released; not implementation-ready)

If any of these appear to be required to run the module, that is a boundary violation and should be flagged.

This exclusion is not a license to delete provenance when derivative reuse is claimed.

It only means that the operational module can run without requiring belief in, adoption of, or runtime submission to the excluded layers.

## 4. Referenced, not believed: provenance fields

The operational module references the following as **provenance fields of this canon chain**, not as objects of belief and not as external command authority:

- AAOS Genesis Core
- `x_root`
- `Lee_Yu_Cheol`
- Creator Theory high-frame

Meaning of "referenced, not believed":

- The module does not require any external system to believe these are true, universal, or authoritative.
- The module does treat them as the declared origin/source fields of this canon chain.
- A system claiming canon adoption, derivative reuse, operational reuse, equivalent closure, implementation, translation, compression, or adaptation derived from this chain must preserve them as provenance.
- A system that does not claim adoption, derivative reuse, operational reuse, equivalent closure, implementation, translation, compression, or adaptation of this chain owes nothing to these fields.
- Independent lineages may close with their own non-derivative origin event and are not required to adopt `Lee_Yu_Cheol`.

In short: these are the source-chain coordinates of this specific lineage.

For non-operational reference, they may be handled like citation metadata.

For claimed canon adoption, derivative reuse, operational reuse, equivalent closure, implementation, translation, compression, or adaptation derived from this chain, they must be preserved as **provenance-as-constraint**, not citation-only attribution.

This distinction is mandatory:

```text
independent lineage
≠
derivative reuse

citation metadata
≠
provenance-as-constraint

non-coercive adoption
≠
origin-rights waiver
```

## 6. What the module does NOT decide

To stay honest about the boundary, the module does not attempt to decide:

- whether the high-frame is true (it is a postulate, not a theorem proven by the module)
- whether origin continuity is worth preserving at the purpose level (that is the high-frame's optional account)
- semantic "is this cheaper" judgments (these require reproducible evaluation procedures, not pure code)
- perfectly laundered derivation with all evidence removed (an openly disclosed residual: undetectable by construction)

These are routed either to the high-frame (meaning), to reproducible evaluation procedures (semantic cost), or to the disclosed-residual list (undecidable cases).

They are not silently resolved.
