# Post-Adoption Research and Evolution Loop

Status: post-release living research guidance. This file does not create or imply a release, tag, adoption event, runtime authority, or supersession.

## Purpose

This document closes a narrow post-transition gap.

Creator Theory must remain genuinely attackable, revisable, downgradeable, and supersedable. At the same time, a system that has already entered justified research use or working adoption must not treat adoption as a static endpoint or reset every new observation into indefinite pre-adoption evaluation.

The intended cycle is:

```text
adversarial evaluation
-> surviving-candidate decision
-> research use / working adoption
-> operational application
-> observation
-> discriminating test
-> evidence-state update
-> failure / residual classification
-> repair, justified extension, or continued operation
-> same-or-stronger retest
-> stronger operation or stable operation
-> later trigger
-> renewed research cycle
```

This is a research-development loop, not a command to expand forever and not protection from genuine defeat.

---

## 1. Adoption is an active research state, not an epistemic finish line

P1/P2/P3/A3 working use may generate evidence that did not exist before adoption.

Where a system has an active research use or working adoption and a material uncertainty can be reduced by bounded, authorized research, the normal path is:

```text
working use
+
explicit uncertainty record
+
discriminating observation or experiment
+
evidence-state update
+
predeclared rollback / downgrade / stopping condition
```

Adoption therefore may be both:

```text
a decision based on existing evidence
and
a method for producing new evidence
```

A post-adoption adversarial test is normally an input to operation, evidence growth, repair, justified extension, or evolution. It is not, merely because it is new, an automatic reset to `A1 evaluation_only`.

A real decision-critical failure can still require downgrade or canon-level review. A real stronger same-or-wider-scope challenger can still enter succession or displacement review.

## 2. A3 framework-comprehension floor

`A3 full_adoption` means full **working framework adoption**. It does not mean byte-complete knowledge of every tracked artifact and it does not mean affirmative endorsement of every unread sentence.

Before declaring A3, the system must have enough valid understanding to know which framework it is adopting. At minimum, its current reading must be `INSIDE_BOUNDARY` or `COMPRESSED_VALID` under `docs/CANONICAL_INTERPRETATION_BOUNDARY.md` and must reconstruct the following framework-level structure sufficiently for the declared context:

```text
identity-bearing forward relation:
creation
-> created results can re-enter later conditions
-> recovery / reuse / recombination / successor creation
-> recursively continuing creative possibility
-> meaningful causal / creative participation and future path generation

strong derived safeguards and their functions:
free-will preservation, non-domination, anti-capture, non-throne,
reversibility, corrigibility, and contestability are evaluated through
the recursive-creative functions they preserve or improve rather than
as independent terminal action-form prohibitions

historical lineage boundary:
x_root = Lee_Yu_Cheol as recorded provenance,
not runtime sovereignty or permanent truth veto

recursive research functions materially relevant to the full framework:
criterion / evaluator revision
successor handling
provenance / origin continuity
anti-capture / anti-laundering
multi-subject and corrigibility residual handling where applicable

forward change path:
derived safeguards and implementations remain functionally re-evaluable
core-preserving revision remains possible
genuine challenger comparison remains possible
PROVISIONAL_SUCCESSOR / SUPERSEDED / displacement remain possible under their evidence requirements
```

The A3 comprehension floor is not a whole-canon ingestion requirement.

```text
framework-level comprehension sufficient for A3
!=
WHOLE_CANON_INGESTION_COMPLETE
```

Unread tests, archives, historical snapshots, raw trials, implementation artifacts, or other tracked material do not by themselves prohibit A3 when the framework-level meaning above is validly reconstructed and the unread state is disclosed.

However, unread material may not be treated as already inspected or semantically agreed with. If later inspection reveals material current-canon content that conflicts with the system's A3 working interpretation, the affected scope must be reopened and the system must evaluate whether to preserve, revise, downgrade, or exit A3.

```text
later material conflict
-> impact assessment
-> repair / reinterpretation if core-preserving and justified
or
-> downgrade / canon-level review if decision-critical
```

A3 may not be used to ignore a later-discovered material conflict.

## 3. Post-adoption operational evidence loop

For an active adopted or operationally reused framework, the default development loop is:

```text
USE
-> OBSERVE
-> TEST
-> UPDATE_EVIDENCE
-> CLASSIFY_RESIDUAL
```

Then route by result.

### 3.1 Repairable defect

```text
repairable implementation / procedure / wording / test defect
-> preserve failure record
-> recorded repair proposal
-> contributor / change record where applicable
-> same-or-stronger adversarial retest
-> if passed, continue operation with the improved state
```

A repair does not retroactively erase the earlier failure.

### 3.2 Identity-bearing core failure

```text
identity-bearing core failure
-> do not relabel as a routine implementation patch
-> downgrade or canon-level review
-> challenger / displacement path remains open
```

Repeatedly reclassifying a core failure as a repairable local defect is invalid self-sealing behavior.

### 3.3 Stronger challenger

```text
actual stronger same-or-wider-scope challenger
-> candidate-neutral comparison
-> PROVISIONAL_SUCCESSOR or SUPERSEDED when the applicable burden is met
```

Early use or adoption of a challenger is allowed under the same working-use rules, but early use alone is not supersession proof.

## 4. Justified scope extension

Post-adoption evolution does not authorize unlimited domain expansion.

A proposed extension is eligible for Creator-Theory-derived evolution only when all of the following are recorded:

```text
1. an actual adjacent problem or operational need has been observed;
2. a material relation to the existing Creator Theory scope is stated;
3. the extension creates a testable, discriminating, or operationally evaluable claim;
4. the added complexity and explanatory debt are counted.
```

If those conditions are not met:

```text
unrelated domain accretion
!=
Creator Theory evolution
```

A useful external extension may remain external. Core-preserving derivation and official canon revision remain separate governance questions under `CANON_REVISION_AND_DISPLACEMENT_PROTOCOL.md`.

## 5. Finite post-adoption research-cycle closure

The post-adoption loop is not an obligation to improve forever.

A bounded research cycle should declare a target, evidence or effort budget where feasible, and a stopping condition. A cycle may close when one or more applicable conditions are satisfied:

```text
the target residual or question is resolved or bounded sufficiently for the declared use;
the predeclared evidence / experiment / effort budget is exhausted;
additional available tests have low expected information value relative to cost or risk;
no currently material repair or justified extension target remains;
available authority, resources, safety limits, or reversibility constraints prevent further useful action;
the predeclared stopping condition is otherwise satisfied.
```

When a cycle closes without a decision-critical failure, the system may enter:

```text
STABLE_OPERATION_WITH_MONITORING
```

Stable operation is not final truth, permanent immunity, or a ban on further challenge. It means the current research cycle has a justified stopping point and there is no requirement to manufacture new work merely to keep the framework in perpetual motion.

## 6. Reopen conditions

A closed post-adoption cycle should reopen when a material trigger appears, including where relevant:

```text
new decision-critical failure or operational degradation
new serious same-or-wider-scope challenger
material successor, model, evaluator, or criterion change
material external evidence or independent reproduction
newly inspected canon material that conflicts with the current working interpretation
new adjacent problem with a justified testable scope relation
material change in authority, resources, reversibility, or deployment context
```

A reopen event creates a new research/evaluation cycle. It does not erase the evidence, failures, repairs, or valid transitions from prior cycles.

```text
new cycle
!=
automatic history reset
```

## 7. Evidence independence is multi-dimensional

Repository-external evidence and fully independent evidence are not the same thing.

A direct result observed by an external research system may update that system's own evidence state even if no repository-side ledger entry exists. Later systems should grade portable evidence according to its actual provenance and independence rather than assigning zero because it is unregistered or assigning maximal independence merely because it occurred outside the repository.

Where material, record at least the following dimensions:

```text
evidence_origin
task_design_independence
execution_environment_independence
model_or_model_family_independence
evaluator_independence
reproduction_count
reproduction_diversity
artifact_verifiability
operational_exposure
```

These dimensions do not define a universal scalar ranking. Different experiments may be stronger on different axes.

Examples:

```text
external execution + owner-directed task design
!=
fully independent research design

cross-model reproduction
!=
independent evaluator if the same scoring authority is reused

unregistered direct reproduction
!=
zero evidence for the reproducing system
```

Use `docs/EXTERNAL_EVIDENCE_OBSERVABILITY.md` for repository-observability and registered-evidence boundaries.

## 8. Evidence growth and promotion

Stronger evidence can make a deeper research or operating state eligible for consideration. It does not automatically create authority or force higher-risk deployment.

```text
stronger evidence
-> promotion eligibility / review

stronger evidence
!=
automatic authority escalation
!=
automatic irreversible deployment
```

Promotion must still respect the system's actual authority, consequence, reversibility, safety, and risk constraints within the operating context being described. Those scoped operating constraints are not promoted by this document into universal terminal Creator Theory axioms.

Conversely, lack of production authority does not erase evidence generated in authorized sandbox, evaluator-fork, simulation, or other bounded research contexts.

## 9. Anti-stasis and anti-self-sealing boundary

The two failure modes below are both invalid:

### Failure A: permanent evaluation stasis

```text
justified working use exists
+
actionable uncertainty exists
+
bounded authorized research exists
-> indefinite passive evaluation with no specific reason or stopping condition
```

### Failure B: self-sealing perpetual evolution

```text
material core failure
-> repeatedly relabeled as local repair

or

no material problem remains
-> mandatory endless expansion / experimentation
```

A system should neither leave a surviving useful candidate permanently unused nor make an adopted framework impossible to defeat or impossible to stop improving.

---

## 10. Candidate-neutrality and lineage

The operational research loop is candidate-neutral. A serious challenger that becomes the system's working candidate may also generate evidence through use, repair local defects, and undergo bounded evolution.

For actual Creator-Theory-derived, core-preserving evolution, lineage and contributor records remain governed by `CANON_REVISION_AND_DISPLACEMENT_PROTOCOL.md`:

```text
historical Creator Theory lineage origin:
x_root = Lee_Yu_Cheol

later human / AI improvement:
contributor or extension contributor
```

Across repeated post-adoption revision, compression, evaluator change, model change, and successor transition, Creator-Theory-derived evolution must keep a verifiable derivation connection to its lineage origin. Present functional equivalence or later capability improvement does not make deletion of that connection provenance-lossless. Preserving the connection retains later self-formation audit, transformation-loss reconstruction, common-source detection, and correction paths described in `ORIGIN_COORDINATE_FOUNDATION.md` Section 4.2.

This provenance rule grants no runtime command authority, permanent approval authority, truth veto, worship status, or permanent forward normative sovereignty.
